## 2. Password hashing

- Many: passlib `CryptContext(schemes=["argon2"], deprecated="auto")` (`backend/app/core/security.py:8`); `hash_password` and `verify_password` at lines 11-16.
- SaaS: `argon2-cffi` `PasswordHasher()` with library defaults, comment states Argon2id, 64 MiB memory, 3 iterations (`modules/saas/apps/api/app/auth/security.py:11,14`). `verify_password` returns False on mismatch and on ANY exception, including a malformed stored hash (`auth/security.py:24-31`).
- Both store a self-describing Argon2 string. Whether passlib verifies an argon2-cffi hash and the reverse, and with which parameters each side produces, was **not tested** (no dependencies here). The design treats it as "to verify in the implementation session" (`docs/IDENTITY-DESIGN.md`).
- Password policy: SaaS minimum length 8 (`modules/saas/apps/api/app/auth/schemas.py:8`, reused by `platform/users.py:60`). Many has no length rule at login (`backend/app/schemas/auth.py:8` is just `password: str`) and none in `create_admin`.

## 3. Sessions, tokens, cookies, logout

### Many: stateless JWT, bearer header
- Token: PyJWT, HS256, claims only `sub`, `exp`, `type="access"` (`backend/app/core/security.py:19-28`). No role, workspace, `jti` or version claim. Decoded with the same secret (`security.py:31-32`).
- Secret and lifetime: `JWT_SECRET: str` (no default, `backend/app/core/config.py:107`), `JWT_ACCESS_TOKEN_EXPIRE_MINUTES: int = 30` (`config.py:108`). `JWT_REFRESH_TOKEN_EXPIRE_DAYS = 7` is defined (`config.py:109`) and referenced nowhere else under `backend/app` (grep). **No refresh endpoint exists.**
- Validation: `get_current_user` (`backend/app/api/routes_auth.py:19-38`) decodes, reads `sub`, loads the user by id, rejects missing or inactive users. The role is read from the database on every request, so a role change or deactivation takes effect at once, but a stolen token stays valid until `exp` (no revocation list).
- Transport and storage: bearer via `OAuth2PasswordBearer(tokenUrl="/auth/login")` (`routes_auth.py:16`). The dashboard keeps the token in `window.localStorage` under `access_token` (`dashboard/lib/auth.ts:6-14`, `dashboard/lib/api.ts:63-68`). CORS: `CORSMiddleware` with `allow_origins=get_allowed_origins()` (`backend/app/main.py:53-55`, `config.py:140-141`).
- Logout is a no-op: returns `{"status": "ok"}` and revokes nothing (`routes_auth.py:103-105`). Nothing server-side supports "logout everywhere".
- `get_current_user` is the single entry point: every JWT-protected dependency chains to it (`backend/app/authz.py:8,54,68,158,173,188`; direct `Depends(get_current_user)` in route files, appendix A). A grep for `get_current_user|decode_access_token|oauth2` outside `backend/app/api/routes_*.py` and `authz.py` finds only the definition of `decode_access_token` (`security.py:31`).

### SaaS: opaque server-side session, HttpOnly cookie, CSRF
- Token: 32 random bytes urlsafe (`modules/saas/apps/api/app/auth/security.py:16,34-35`); only the SHA-256 is stored (`auth/security.py:38-40`) in `sessions` (`core.py:55-71`: `token_hash` unique, `expires_at`, `revoked_at`).
- Cookie: name `chatbot_session`, `HttpOnly`, `SameSite=Lax`, `path=/`, `Secure` from setting (`auth/cookies.py:18,23-40`). Host-only (no `domain=` set), consistent with `docs/DEPLOY-OUTLINE.md` open decision 3.
- CSRF: double-submit cookie `chatbot_csrf` (readable by JS, `cookies.py:53-68`) compared with header `X-CSRF-Token` in constant time, fails closed (`cookies.py:71-80`). Applied to cookie-authenticated writes (`CsrfOk`/`Csrf` in appendices B and C).
- Validation per request: `get_current_user` looks up the token hash, not revoked, not expired, user active (`cookies.py:83-105`).
- Lifetime: `session_lifetime_seconds` default 14 days, allowed 300 s to 90 days (`modules/saas/apps/api/app/core/config.py:36`). Expiry is set once when the session row is created (`auth/service.py:195`); no sliding renewal code was found.
- Login rotates: new session issued and the presented token revoked (`auth/service.py:101-103`). Logout revokes the presented session, idempotent, CSRF-checked (`auth/router.py:121-133`, `service.py:107-111`).
- Revoke-all exists only as a service method (`service.py:215-220`), called from staff password reset (`platform/users.py:312`) and staff deactivate (`users.py:322`). There is **no user-facing "log out everywhere"**. `change-password` revokes all OTHER sessions and rotates the current one (`service.py:148-159`).
- Web dashboard to API: same-origin through the Next `/api` rewrite (`docs/DEPLOY-OUTLINE.md` decision 3).

## 4. Rate limiting and lockout

- Many login: Redis fixed window, two buckets: per email+IP 5 per 60 s and per IP 20 per 900 s (`backend/app/core/config.py:96-99`, `backend/app/services/rate_limit_service.py:122-142`). A limited attempt writes audit `login_rate_limited` and returns 429 (`routes_auth.py:47-59`). **Fails open** if Redis errors (`rate_limit_service.py:73-75` returns `allowed=True`). Client IP is `request.client.host` only; raw forwarded headers are ignored (`rate_limit_service.py:35-39`). No account lockout.
- SaaS login: Postgres fixed window, **per IP only**, key `login:{ip}`, default 10 per 300 s (`modules/saas/apps/api/app/auth/router.py:37-52`, `core/config.py:41-42`, counter SQL `core/ratelimit.py:32-53`). The counter is committed separately so failures count (`router.py:41-42,50`). No per-email bucket and no lockout. Change-password failures are throttled per user (`auth/service.py:172-182`).

## 5. Enumeration and timing behavior (observed in code)

- Many login: same 401 text for unknown email and wrong password (`routes_auth.py:61-76`). Always runs `verify_password` only when the user exists (short-circuit `not user or not verify_password(...)`, line 62), so unknown emails skip the Argon2 cost (timing difference).
- SaaS login: same 401 `INVALID_CREDENTIALS` text for unknown, wrong password, inactive, and "all memberships revoked" (`auth/service.py:98-100,200-213`). Same short-circuit (`user is None or not verify_password`, line 98): timing difference for unknown emails.
- SaaS `register` reveals registered emails with `EMAIL_TAKEN` 409, documented as an accepted MVP trade-off (`auth/service.py:59-60,81-82`). Reachable only with a valid invitation or when `self_serve_signup` is on (default off, `core/config.py:31`; `modules/saas/docs/02-USER-JOURNEYS.md:3`).
- SaaS invite creation reveals whether an account exists: it refuses with "No account exists for this email. Ask your platform contact to create it." (`modules/saas/apps/api/app/tenants/service.py:131-136`), a tenant-admin-visible oracle.

## 6. Roles, workspaces and tenants

### Many
- Four roles: `owner`, `admin`, `operator`, `viewer` (`backend/app/roles.py:1-6`); `normalize_role` maps `"user"` and any unknown or empty value to `viewer` (`roles.py:9-13`).
- Permission map `ROLE_PERMISSIONS` (`backend/app/authz.py:14-46`): owner has manage_users, manage_campaigns, delete_campaigns, manage_accounts, disconnect_accounts, delete_accounts, view_audit_logs, retry_messages, manage_contacts, manage_templates, run_campaigns; admin has the same minus manage_users and delete_accounts; operator has manage_campaigns and view_audit_logs; viewer has view_audit_logs. `manage_users` is defined but no route uses it (appendix A).
- Two enforcement styles live side by side:
  1. **Global**: `require_permission` / `require_role` read `users.role` (`authz.py:49-76`). Used by Instagram, campaigns, messages, conversations, dashboard stats.
  2. **Workspace-scoped**: `require_workspace_role`, `require_workspace_permission`, `require_workspace_any_permission` (`authz.py:96-205`) read the membership role for the workspace named in the `X-Workspace-Id` header (missing header 400, bad UUID 400, no membership 403: `authz.py:103-128`). The comment states this was introduced for WhatsApp and Facebook only; "Instagram and every other still-global route keep using require_permission / require_role above, unchanged" (`authz.py:79-84`).
- Workspaces: `workspaces(id, name, slug unique)` (`backend/app/models/workspace.py:11-26`); `user_workspace_memberships(user_id, workspace_id, role default operator)` with unique `(user_id, workspace_id)` (`backend/app/models/user_workspace_membership.py:11-42`, unique constraint at `:21-23`, role default at `:34`). Migration `0017_workspace_membership.py` is purely additive and copies each `users.role` into a membership in the `default` workspace (`backend/alembic/versions/0017_workspace_membership.py:7-13,79`). `GET /workspaces/me` lists the caller's memberships (`backend/app/api/routes_workspaces.py:13-40`); its docstring says the dashboard picks the `default` workspace and has no switcher (`routes_workspaces.py:18-25`).
- **Data scoping gap (important):** the global routes do not filter by workspace. `grep -c workspace_id` per route file: `routes_campaigns.py` 0, `routes_conversations.py` 0, `routes_messages.py` 0, `routes_instagram.py` 3, `routes_dashboard.py` 16, `routes_facebook.py` 19, `routes_whatsapp.py` 9, `routes_whatsapp_outreach.py` 67. Example: `GET /instagram/accounts` returns `db.query(InstagramAccount).all()` for any logged-in user (`backend/app/api/routes_instagram.py:114-121`). The data IS tagged: `workspace_id` is a non-null FK on `instagram_account` (`backend/app/models/instagram_account.py:18-20`), `campaign` (`campaign.py:17`), `conversation` (`conversation.py:79`), `lead` (`lead.py:53`), `whatsapp_account` (`whatsapp_account.py:44`), `facebook_page` (`facebook_page.py:24`).
- No agency and no location concept exists in Many (no model or column; grep of `backend/app/models`).
- No platform-staff concept in Many: a global `admin`/`owner` user is the de-facto staff and, on global routes, sees all data (previous bullet).

### SaaS
- Tenant roles: `viewer`=1, `editor`=2, `admin`=3 (`modules/saas/apps/api/app/core/tenancy.py:20-21`). There is **no owner role**. `is_platform_staff` is separate from tenant roles (`platform/staff.py:1-10`, `core.py:45-47`).
- Tenancy: `tenants(id, name, slug, retention_days, plan_label, quota_overrides, status, ...)` (`core.py:74-104`); `memberships(tenant_id, user_id, role default viewer, status)` (`core.py:107-133`). The platform API and UI call a tenant an "organization" (`platform/users.py:62-100`, audit actions `platform.organization.*` observed in `record_audit` calls).
- Tenant dependency: resolves tenant from the path, requires an active membership, returns 404 (not 403) for hidden tenants (`core/tenancy.py:62-82`); platform staff pass without a membership and bypass `require_role` (`tenancy.py:45,80-82`); inbox write actions require a real membership even for staff (`tenancy.py:86-91`).
- Per-route minimum role is a reviewed table, `TENANT_ROUTE_ROLES` (`core/permissions.py:3-145`), attached to routes at startup (`modules/saas/apps/api/app/main.py:75-91`) and read per request (`tenancy.py:84`). Appendix B lists all 93 entries.
- Value `platform_staff_only` (34 of 93 entries) means clients cannot call it: bot create/edit/delete, tone and rules, readiness, all knowledge sources, ingestion, jobs, documents, revisions and publish, playground, feedback, all RAG settings (appendix B). `require_operator` enforces it (`tenancy.py:52-54`: "Only platform staff can control the bot.").
- `ChannelConnection` links a tenant and bot to a Many channel: `tenant_id`, `bot_id`, `channel`, `many_base_url`, `many_channel_ref`, encrypted secret, health fields (`modules/saas/apps/api/app/db/models/channels.py:28-47`). ## 10. Duplicates and conflicts between the two apps

What the code allows (no production or staging data was available, so counts are unknown):
1. **Same email in both apps** is possible: the databases are separate (Many Postgres 15, SaaS 17, `docs/MERGE-PLAN.md`), no shared key exists.
2. **Case variants**: Many treats `A@x.com` and `a@x.com` as different users (`user.py:17`, plain unique `String`); the SaaS treats them as one (`core.py:41`). A single Many database can therefore already hold two users that collapse to one SaaS user.
3. **Different roles for the same person**: Many role `owner|admin|operator|viewer` (global plus per workspace) vs SaaS `viewer|editor|admin` per tenant plus staff flag. There is no owner in the SaaS; there is no `editor` in Many (closest is `operator`). Many `manage_users` has no route.
4. **Different hashes**: both Argon2 strings, parameters not compared (section 2). A hash may be portable or not; not tested here.
5. **Account state mismatch**: Many `is_active` single flag; SaaS also treats "all memberships revoked" as inactive for login (`auth/service.py:204-213`).
6. **Default privilege**: Many `users.role` defaults to `admin` (`user.py:20`) and `create_admin` defaults to `admin` (`create_admin.py:22,54`).
Read-only SQL for the owner to count real duplicates later is in the design doc (migration section); it was not run.
